# Academy application internationalization

This guide defines localization of Academy's application interface. It does not define course translations. Application locale controls navigation, controls, validation, errors, accessibility text, dates, numbers, and system messages. `Course.sourceLanguage` and translation records describe learning content and remain independent: a Spanish Academy interface can display an English course.

## Current-state audit

Before this foundation, `vue-i18n` was installed but configured inline in `main.ts` with five English strings. The rest of the frontend rendered English literals directly. A focused source scan found the largest hotspots in `PluginManagementPage`, `DashboardPage`, `HomePage`, `LessonPage`, `AuthoringDraftStructurePage`, `AdminPage`, `PublishedCourseReaderPage`, `AuthoringDraftCreatePage`, `AuthoringHomePage`, `AuthoringLessonContentEditor`, and `StructureDetail`. These contain page copy, controls, placeholders, state messages, dialogs, and accessibility labels. Counts are approximate because templates, technical constants, and tests also contain strings.

Other recurring debt:

- Authoring Details, Content, Prerequisites, Members, Assessments, and Review assemble validation and operational messages locally.
- Several pages create `Intl.DateTimeFormat('en' | 'en-GB', ...)`, while others rely on the browser default. Duration formatting in `courses.ts` assembles English `hr` and `min` fragments.
- Accessibility labels, tooltips, live-region announcements, empty states, and dialog text are mostly hardcoded alongside visible copy.
- Known API problem codes are sometimes mapped safely, but many features still select English prose inline. Arbitrary backend `title` or exception messages must not become translated UI.
- `frontend/src/i18n/languages.ts` supports course/source-language entry. It is not an application-locale registry and must not be used to select interface language.

Migration is intentionally incremental. M-I18N.1 migrates the AppShell navigation and session controls, and removes English defaults from reusable dialog and previous/next compositions. Remaining pages migrate with their feature milestones.

## Framework and source layout

Academy uses Vue I18n in composition mode. English is the explicit source locale.

```text
frontend/src/i18n/
  application.ts       # Vue plugin, locale changes, document language
  registry.ts          # canonical supported locales and loaders
  preference.ts        # resolution and persistence boundary
  formatters.ts        # dates, numbers, durations, relative time
  errors.ts             # validation/API-code mapping boundary
  pseudo.ts             # pseudo-localization transform
  locales/
    en/
      common.ts
      navigation.ts
      session.ts
      authoring.ts
      courses.ts
      dashboard.ts
      validation.ts
      errors.ts
    en-XA.ts
```

Message keys describe stable product semantics, for example `authoring.structure.addModule`, not control appearance or literal English. Do not concatenate grammatical fragments. Use interpolation and Vue I18n pluralization:

```ts
t('authoring.structure.lessonPosition', { current, total })
t('common.counts.lesson', count)
```

## Locale model and resolution

Locale identifiers are canonical BCP 47 tags. `en` is both the default and fallback locale. Startup resolves locale in this order:

1. validated preference stored under `btg.academy.application-locale`;
2. the first supported production locale matching `navigator.languages`;
3. `en`.

All storage access goes through `preference.ts` and tolerates unavailable or invalid storage. `useApplicationLocale()` is the integration boundary for a future profile/settings selector. It updates Vue I18n, persistence, and document language together. A future server profile can replace the storage implementation without coupling UI locale to course data.

There is no production language selector yet because Academy has no appropriate account-settings surface. Do not add a developer dropdown to navigation. When settings exist, label the control “Interface language” and source options exclusively from `applicationLocales`.

`applicationLocales` is the single registry for ID, native name, text direction, production visibility, and message loader. English is eager because it is the fallback; non-default bundles are lazy-loaded. `en-XA` is a non-production pseudo-locale available to tests and explicit development use.

## Formatting

Use `useApplicationFormatters()` inside components, or the pure formatting functions in non-component code.

- `date`: `short`, `date`, and `dateTime` semantic presets.
- `number`: `count`, `decimal`, and `percent` presets.
- `duration`: localized `Intl.NumberFormat` unit output for hours/minutes.
- `relativeTime`: `Intl.RelativeTimeFormat` with automatic today/yesterday-style wording.

Do not call English-specific `Intl` formatters or manually insert punctuation/unit labels in migrated UI. Course content dates are still formatted using the application locale; course language does not control interface formatting.

## Validation and API errors

Validators should return stable codes plus parameters, then map codes through `validationMessageKey`. They should not return final English prose. Known API problem codes map to translation keys at the feature boundary. `applicationErrorKey` provides safe status fallbacks. Unknown errors render `errors.generic`; never translate or expose arbitrary backend exception text.

The backend currently exposes a mixture of useful stable `problem.code` values and English `title`/detail fields. Expanding stable problem-code coverage is backend migration debt, not a reason to use server prose as interface copy.

## Component responsibilities

- Product and feature components call `t()` and supply translated visible and accessible labels to Btg components.
- Generic Btg primitives do not import product namespaces or bake in English. Labels such as dialog trigger/dismiss text, menu names, drag-handle names, and previous/next navigation labels are caller-provided.
- Application compositions may use the `common` namespace when the wording is genuinely shared.
- Accessibility strings follow the same rules as visible strings. This includes `aria-label`, descriptions, visually hidden text, tooltips, live regions, and reorder announcements.
- Reorder features own translated announcements with complete parameterized messages; primitives own the accessible surface but not domain nouns.

The root `lang` and `dir` attributes are updated on locale changes. New reusable CSS should use logical properties (`padding-inline`, `margin-inline`, `inset-inline`) when practical. RTL is not yet supported, but direction metadata belongs in the locale registry.

## Pseudo-locale and tests

`en-XA` accents and lengthens messages while preserving `{interpolation}` placeholders. It makes untranslated English and fixed-width assumptions visible without pretending to be a production translation.

Use `createTestI18n()` or `renderWithI18n()` from `frontend/src/test/i18n.ts`; component tests must not hand-roll message objects. At least one reference test should render each migrated surface with `en-XA` and assert the original English control is absent. Prefer focused semantic assertions over snapshots of every word.

Development enables Vue I18n missing/fallback warnings. Production falls back to explicit English messages. Missing keys must be fixed rather than hidden with component-local fallback prose.

## Adding a production language

1. Add domain message modules matching the English key structure.
2. Add one lazy loader, canonical ID, native name, direction, and `production: true` entry to `applicationLocales`.
3. Test locale matching, interpolation, pluralization, formatters, `<html lang>`, and representative layouts at 320px and 200% text.
4. Run the pseudo-locale suite as well as the new locale suite.
5. Add the interface-language control only in the shared settings surface; never reuse a course-language picker.

## Enforcement

Automated enforcement is deliberately focused to avoid classifying IDs, API values, test selectors, and technical constants as translatable copy. The shared test helper and pseudo-locale reference test enforce the migrated boundary. Code review must reject new user-facing literals in migrated components and raw English defaults in Btg primitives. A source lint rule should be added only when it can operate on Vue template AST nodes with an explicit allow-list and low false-positive rate.

For each feature migration, inventory visible text, accessibility text, errors, validation, dates, numbers, and announcements; add domain keys; migrate complete messages; run English and pseudo-locale tests; then remove obsolete local formatters.
